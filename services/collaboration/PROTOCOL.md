# Research collaboration protocol v1

All HTTP paths below start `/v1/collaboration`. All requests except ticket redemption require the existing `Authorization: Bearer <account-token>` header. Responses and assets carry `Cache-Control: no-store`. Never pass an account token in a URL. Errors: `{error:{code,message,retryable,details?}}`; 400 invalid input, 401 expired session/ticket, 403 access/role denied, 404 unknown object, 409 stale epoch/state/lease, 413 size exceeded, 429 rate limit. Times are Unix milliseconds (account sessions remain existing seconds).

## Document exports

`packages/dsh-research-collaboration/document.js` exports `createDocument(canvas): Y.Doc`, `encodeDocument(doc): Uint8Array`, `decodeDocument(bytes): Y.Doc`, `projectDocument(doc): Canvas`, `applyCanvasDiff(doc,before,after): Uint8Array`, `freezeSnapshot({canvas,history?}): Snapshot`, `mergeDocumentUpdate(doc,bytes,tombstones?:Set<string>): Uint8Array`, `validateCanvas(canvas): void`. `protocol.js` exports `PROTOCOL_VERSION`, `LIMITS`, `toBase64(bytes)`, `fromBase64(string)`, `validatePresenceHints(value,canvas)`.

Canvas has `{files: Node[], artifacts: Node[]}`. Nodes require string `id`; editable text fields use Y.Text, fields use nested Y.Map, lists inside component data use Y.Array. Top-level `files` and `artifacts` are maps indexed by node ID. Local diff MUST receive the last local projected canvas and the next local canvas; untouched fields are not rewritten. Snapshot `tombstones` is a read-only string array of `collection:id`; clients may use it to filter their pending changes but can never clear it. Deleted IDs are permanent within this board: use a fresh ID to restore explicitly. No tasks, roles, credentials, local paths, selection, viewport or execution logs in the document. `freezeSnapshot` copies allowed fields and history, removes machine state, and returns a deeply frozen independent value. `mergeDocumentUpdate` validates on a clone before mutating the live doc, preserving server tombstones.

## HTTP

- `GET /me` -> `{user:{userId,publicId,username}}`; publicId exactly ten digits, including leading zero. Existing users provision lazily and race safely. Account API remains backward compatible.
- `POST /users/lookup` `{publicId}` -> `{user}` exact ten-digit lookup (UI strips display spaces); max 5/minute/account.
- `POST /boards` `{operationId,title,sourceRevision,capturedAt,snapshot:{canvas,history?},uploadId?,assets?:[{assetId,name,contentType,dataBase64}]}` -> `{board,created}`. operationId is account-scoped, retries return the existing frozen copy. Pass uploadId from the staging routes below for large files; inline assets are only a small-payload convenience. All declared assets must upload and every node asset reference must resolve before activation. `capturedAt` ISO string; sourceRevision opaque string; never submit a local session ID/path. Optional initial assets must have caller-generated UUID IDs (local->asset reference mapping is made before capture).
- `GET /boards` -> `{boards}` accessible boards, each includes `role`.
- `GET /boards/:boardId` -> `{board,snapshot:{canvas,history},documentUpdate,seq,tombstones,members,messages,tasks,pendingInvitations}`. documentUpdate is base64 Yjs state, authoritative starting point for a connection. `pendingInvitations` is owner-only authority outside the document: `[{invitationId,invitee:{userId,publicId,username},role,version,expiresAt,status:"pending"}]`, restricted to current epoch, nonexpired pending invitations. Nonowners receive `[]`; role changes and revocations use existing `invite` / `revokeInvitation` commands and refresh this list.
- `POST /boards/:boardId/commands` -> command response below. Body always `{action,operationId,epoch,...}`. operationId 1–128 safe identifier characters; user-scoped idempotency. Reads after revoke are denied; `GET /boards/:boardId/receipts/:operationId` remains allowed to its submitter and returns only `{operationId,accepted,seq,epoch}` (no board content).
- `POST /uploads` `{operationId}` -> `{uploadId,expiresAt,boardId:null|string}`. An account-owned staging operation lasts 24h. `PUT /uploads/:uploadId/assets/:assetId` sends raw bytes with `X-Asset-Name: encodeURIComponent(filename)`, `X-Asset-Size: <decimal byte length>` and `Content-Type`, returning `{assetId,size,contentHash,name,contentType,version:1}`. R2 streams are size checked without buffering a 50 MiB file. Upload all files, then create with uploadId; failed creation retains staging for retry. Successful creation atomically assigns assets and closes staging. Concurrent/repeated asset IDs are immutable: matching content is idempotent, different bytes return 409.
- `POST /boards/:boardId/assets` raw bytes with `X-Operation-Id`, `X-Sharing-Epoch`, `X-Asset-Name: encodeURIComponent(filename)`, `X-Asset-Size`, `Content-Type` -> `{asset}`. Editors/owner only. `GET /boards/:boardId/assets/:assetId` proxies private bytes after live permission check. No presigned/public URL. Assets are immutable and board-scoped.
- `POST /notifications/feedback` accepts an authenticated sender's `{operationId,message}` (1–2000 characters) and returns `{notificationId}` after the recipient notification and live-delivery outbox row are saved. The service resolves the recipient account `hyf90`. Retrying an operation with the same text returns the same notification.
- `GET /notifications?after=0&limit=50` -> `{notifications,cursor,unreadCount,pendingCount}`; monotonic numeric cursor, oldest unseen first, pending invitations at their current event version always additionally included even before cursor. Pending reminders do not consume the chronological page limit or advance its cursor; clients dedupe notificationId + eventVersion. Each notification includes `notificationId,eventVersion,type,boardId,boardTitle,actor,invitation?,createdAt,readAt`. Invitation current state is hydrated from D1, including expiry. `POST /notifications/read` `{notificationIds?:string[]}` marks specified or all read; does not process invitations.
- `POST /invitations/:invitationId/respond` `{operationId,version,decision:'accept'|'decline'}` -> `{invitation,memberCount,boardId}`. Wrong recipient denied. Duplicate acceptance is idempotent. Old permission version rejected. Invites expire after 7 days; cancelled/expired/declined replies return 409 and `details.invitation` current state.
- `POST /tickets` `{scope:'board',boardId}` or `{scope:'notifications'}` -> `{ticket,expiresAt,url,epoch?}`. Single use, 30 seconds, bound to session hash/user/scope/board/epoch. `url` is a relative `/v1/collaboration/connect?ticket=...`; convert protocol to wss and resolve against configured collaboration origin.
- `GET /connect?ticket=...` with WebSocket upgrade redeems once. Live account session and membership/epoch are checked before welcome and on every message/broadcast/read. No automatic replay before the welcome permission check.

## Board commands

Every mutation returns `{action,operationId,seq,epoch,...result}` only after a durable transaction. Always use latest board.sharingEpoch as `epoch`.

| action | additional body | result / authority |
|---|---|---|
| `update` | `update` base64 Yjs update | `{documentUpdate}` canonical merged state; editor/owner |
| `refreshPause` | `paused:boolean` | `{board}` owner; interrupts refresh tasks when paused; board.refreshPaused is authoritative |
| `rename` | `title` | `{board}` owner |
| `invite` | `publicId,role:'editor'|'viewer'` | `{invitation}` owner; same pending role returns same invitation; role change increments version and notification |
| `revokeInvitation` | `invitationId` | `{invitation}` owner |
| `memberRole` | `userId,role` | `{member}` owner, cannot target owner |
| `removeMember` | `userId` | `{removedUserId}` owner; stops leases, closes connections |
| `leave` | none | `{removedUserId}` own non-owner membership |
| `archive`, `restore` | none | `{board}` owner; archive stops tasks and cancels pending invites, read access retained |
| `cancel` | none | `{board}` owner; ownerOnly, epoch++, cutoffSeq, revoked memberships/invites/leases; old writes denied |
| `reopen` | none | `{board}` owner; shared, epoch++, no automatic member/invite restoration |
| `message` | `text,context?:{scope:'board'|'references',references:[{collection,nodeId}]}` | `{message}` editor/owner; trusted author, immutable submitted message |
| `taskCreate` | `requestMessageId,targetId?,source?:'manual'|'refresh',targetCollection?:'artifacts'|'files',refreshScheduleId?` | `{task}` request author only; captures accepted context seq and immutable snapshot, target content version |
| `taskClaim` | `taskId,executorId` | `{task,leaseToken}` initiator only; session + executor lease, 30s |
| `taskHeartbeat` | `taskId,leaseToken` | `{task}` same live executor; extends 30s |
| `taskResult` | `taskId,leaseToken,text?,node?` | `{task}` same executor; immutable result, server applies node only if target exists/version matches; otherwise `pendingResult`/`targetDeleted` retained in task |
| `taskApplyResult` | `taskId` | `{task}` editor/owner explicit recovery; retained result preserves current target geometry, deleted target receives a new ID, repeat returns appliedTargetId |
| `taskYield` | `taskId, executorId, executorStopped:true, leaseToken?` | drained executor checkpoint acknowledgement; same originating session can recover it after lease expiry |
| `taskStop` | `taskId` | `{task}` initiator or owner; interrupts lease |

`task.contextSnapshot` is available only in authenticated board snapshot/claim, never notification. Refresh tasks require a target and are blocked while the owner pauses refresh; at most one pending/running refresh task exists per target. No task handoff: interrupted tasks require explicit new request/task. Owner archive/cancel and member removal/downgrade interrupt corresponding execution. Result nodes use document allowlist, cannot replace server authority; replies carry requestMessageId.

## WebSocket JSON

Server first sends `{type:'welcome',scope:'board',...snapshotResponse,presence:[{userId,username,role,joinedAt}]}` or `{type:'welcome',scope:'notifications',...notificationPage}`. Send board commands as `{type:'command',requestId,command:{action,operationId,epoch,...}}`; server responds `{type:'ack',requestId,...commandResponse}` or `{type:'error',requestId,error}`. Accepted changes broadcast `{type:'boardChanged',...snapshotResponse}` (full bounded checkpoint; clients apply documentUpdate through Yjs). Controls may send `{type:'accessRevoked',reason,epoch}` then close 4003. Server can send `{type:'presence',presence}`. Client `{type:'presence',cursor?:{x,y}|null,selectedIds?:string[],previews?:[{collection:'files'|'artifacts',nodeId,x,y,width,height}]}` updates a 30s lease; user identity is server supplied; ping every 10s via `{type:'ping'}` also refreshes presence and returns `{type:'pong'}`. Connections are hibernation sockets with serialized attachment. Presence dedupes account across connections, removes stale users by DO alarm <=30s. Notification events `{type:'notification',notification}` are at-least-once; dedupe notificationId + eventVersion and backfill HTTP cursor after reconnect. Notification ping revalidates sessions.

## Limits and storage

11 members/board (final Figma 304:980 / 306:569, three avatars plus eight); 7-day invite expiry; 20 new invites/day/inviter, declined re-invite cooldown 24h. Max 1,000 nodes, 1 MiB projected canvas or encoded Yjs checkpoint, 1 MiB single Yjs update, 16 KiB message, 50 MiB individual asset, 1 GiB aggregate assets per board, 25 MiB aggregate inline creation request, 100 history records. Notification retention 90 days except pending. Combined authoritative state and each operation receipt are checked against 1,800,000 UTF-8 bytes before any D1 mutation; oversized history/document/task accumulation returns 413, with no silent truncation or partial board activation. This conservative bound stays below [D1’s 2,000,000-byte per-row/string/BLOB limit](https://developers.cloudflare.com/d1/platform/limits/). Large source documents belong in versioned private assets. D1 is the atomic authority for board checkpoint/control/receipts/outbox; per-board DO serializes commands and mirrors committed checkpoint to SQLite-backed storage for recovery. Outbox persists before response, retries by alarm and notification reconnect. R2 incomplete creation objects are tracked and reclaimed after 24h; active board assets are never reclaimed by that path. Existing account login/model credentials and billing contract remain unchanged. Wrangler config is deployment-ready but deployment and shared-client build are outside this task.

Task-claim replay is additionally bound to the current epoch, original still-live session, executorId, unexpired lease and running task. Reusing the same operationId for another action is rejected. Cancel/reopen retries may return the original safe owner receipt after the epoch advances; revoked users can access only the content-free receipt endpoint. Document projection preserves completed containerSpec/sourceText/generationSources and geometry; copied running components become interrupted with “复制时未完成”. Existing node IDs and nested shared arrays preserve separate table-cell and chart-series edits. Array insertion/removal preserves unchanged surrounding shared children; arbitrary concurrent reorder is not a first-version UI operation.

Review fix round: staging activation and cleanup both acquire the unique `research_upload_claims.upload_id`. An activation claim requires an unexpired, unassigned upload and is part of the board/member/asset D1 batch; a losing claim aborts that whole batch with `UPLOAD_ALREADY_CLAIMED_OR_EXPIRED` (409). Cleanup claims before deleting R2 bytes and resumes an interrupted cleanup claim on its next run. Assets are assigned only to the matching activation claim, never reassigned between boards.

The document boundary validates actual nested Y.Map/Y.Array/plain Y.Text plus encoded struct history; rich-text formatting, text block attributes, embeds, binary/subdocuments and XML shared types are unsupported and rejected. Existing legitimate Yjs identities are retained when accepting an update. The root and shared package both pin Yjs 13.6.32.

Task result CAS deliberately uses the entire target-node revision, including geometry. Moving/resizing the target during generation can therefore leave the result as `pendingResult`; it preserves the user's current position/size and retains the generated result for explicit application. This conservative behavior does not distinguish content and geometry revisions in this version.

### Ephemeral gesture hints

Presence hints are excluded from the CRDT, operation receipts and undo. The normalized `{cursor,selectedIds,previews}` must be at most 8,192 UTF-8 JSON bytes, with at most 100 selected IDs and 100 previews. IDs are 1–128 safe identifier characters; cursor/position coordinates are finite and bounded to ±10,000,000; width/height are positive and at most 20,000. A preview must reference a currently existing node in its stated collection, with no duplicate collection/node pair. Unknown fields are rejected. Viewers may publish cursor/selection hints but cannot publish editing previews; live membership, role, account session and epoch are checked on every message. The full proposed socket attachment has an additional 16,000 UTF-8 JSON-byte preflight before serialization. Real workerd integration covers an accepted hint over 8,000 bytes and rejects oversized hints without closing the socket.

Server assigns `previewExpiresAt = now + 3000` and `previewSeq = current seq`; recipients ignore expired previews and previews whose sequence differs from their authoritative snapshot. Ping extends presence membership only, not the preview deadline. The page sends at most every 100 ms with a trailing frame and trims the end of the temporary selection/preview subset until it fits 8,192 bytes. This never trims durable canvas changes or lowers the 1,000-node document limit. Finish, cancel, blur, permission/account loss and disconnect clear temporary hints; real `moveNodes`/`resizeNode(..., false)` sends only previews and `workspace.persist()` commits the final gesture once. Remote canvas hydration waits behind a held local gesture so its diff retains the actual observed local branch.

Notification IDs identify events, while invitation IDs identify current authority. When authenticated events carry a later invitation version (or terminal state at the same version), clients apply that invitation descriptor to all retained events for the same invitation. An already-visible bubble updates in place, preserving its remaining timeout/focus and removing unavailable actions.


## Portable context and desktop execution (Task 4)

`message.context` is derived from the accepted canvas. Canonical references retain collection/nodeId, display name, nodeVersion and authorized assetId/assetVersion or artifact text/kind; unknown/duplicate IDs and local path fields are rejected. `message.contextRevision` records the accepted sequence, and `taskCreate` rejects selected references whose node versions changed after message acceptance. History and artifact generationSources participate in asset closure; every referenced cloud asset must belong to this board. Saved human records remain display/evidence data, never imported runtime prompts.

A generated container can carry `refreshScheduleId`. A refresh task must name the same token as its current acknowledged target; only the desktop that durably created that schedule runs it, with no recipient timer or automatic handoff. Owner pause also stops active refresh leases. New original/personal copies reset refresh settings.

The main process owns a separate durable request-step journal. Every message/task/claim/result step writes immutable operationId, epoch and body before the fixed command endpoint, and stores the complete accepted receipt before advancing. Renderer `request.submit` returns `{accepted:true,clientMutationId,requestMessageId,taskId,state}` after durable message acceptance. `state` is `messageAccepted`, `taskCreateFailed` or `taskAccepted`; taskCreateFailed includes explicit uncertainty and retains retry using the original request identity. `request.list` reconstructs unresolved own requests after reload. An explicit retry of interrupted/uncertain execution retains the message identity and creates a new task attempt with a warning that prior external work may already have run.

Main-to-local-runtime uses a separate private bearer and fixed POST `/sherlock/research-boards/{history,fresh,fresh-check,fresh-release,start,inspect,cancel}` routes. Only loopback, same-origin when an Origin is supplied, bounded JSON and no forwarded identity are admitted. `history` exports the complete saved append-origin human transcript; supported text/envelopes are normalized, unsupported embedded media fails explicitly without truncation. `fresh` proves a newly created empty Session; `fresh-check` rechecks its transcript and temporarily blocks append on that exact Session until `fresh-release` (30-second defensive expiry), so finalize cannot race a new prompt. Completed personal imports are local data and remain readable after logout/revocation.

Runtime starts use the cloud taskId as a fixed local task identity. A lost start response is resolved through `inspect`, not a second model invocation. Persisted queued/running tasks restored after runtime restart become interrupted and are never replayed automatically. Durable command identity proves message/task deduplication; it does not claim exactly-once external model side effects after an unprovable runtime failure. The production executor drives root Q&A/board turns through the sender’s existing main agent; component tasks retain the subagent adapter and native container/summary/mind-map output. Direct legacy research/workbench routes reject historical shared session IDs through main authority.

## Shared conversation main agent and queue (2026-09-16)

Root tasks (no targetId) are classified by the server as `conversation:true`, with a durable `queueOrder`. Exactly one root conversation may hold a lease, and it waits for earlier workbench component tasks to settle. A root's own component children may execute under the existing per-component leases. `taskClaim` returns `CONVERSATION_BUSY` until the turn is eligible; clients retain the same idempotent claim operation and wait. The initiator's local main agent executes root turns with its normal tools/delegation. Component output still uses the existing child adapter and format repair.

At root claim time, the server constructs a fresh canvas/history/message snapshot. Other pending or deleted requests and messages not yet admitted to a task are excluded; the current request is last. Prior completed answers are included. Queue text, authorship and task order travel through the existing durable snapshots/WebSocket broadcast.

`queueEdit {taskId,text}`, `queueDelete {taskId}`, and `queuePromote {taskId}` require an editable member who owns the pending task. Edit changes only message text; references keep their admitted identity. Delete leaves a tombstoned message for recovery/audit and interrupts its pending task. Promote moves the message ahead of waiting conversations and sets `yieldRequested` only on the running main conversation. Components remain independent. It grants no second lease. The executor retains its native session history, drains its current chat turn, and acknowledges `taskYield {taskId,executorStopped:true,leaseToken}`. The same logical task returns to pending with an incremented `resumeCount`, behind the priority messages and ahead of ordinary queued work. Its owner automatically reclaims it with a fresh lease and execution-attempt ID, continuing from saved context after priority work finishes. Lost acknowledgements reconcile against the authoritative resume count; stale leases cannot publish results. Explicit stop takes precedence over yield. Ordinary taskStop of a running conversation requests stopping; only the leased executor's acknowledgement ends its ownership. An authorized task with an outstanding yield keeps its slot after lease expiry until its originating authenticated executor acknowledges drain; lease timeout alone never admits overlapping work. Reconnect/restart replays the durable acknowledgement using the same operation and executor identity. Ordinary expired tasks and revoked access retain interruption recovery.

Each successful conversation `taskClaim` persists `conversationDisplayOrder` as the committed board sequence. Yield retains that value; reclaim advances it only after priority work finishes. Clients move the whole request/answer turn according to this durable execution order, so completion, reload and other members agree. Older server snapshots without the field use task completion/pause timestamps and authoritative answer insertion order; no new message or duplicated answer is generated.

Never-started pending local requests resume when their author's board is reopened. Started/uncertain executions still require explicit retry. An offline author at the queue head retains their position until reconnect/delete. Clients reject a root claim that lacks conversation authority before invoking the model, so the collaboration Worker must be upgraded before clients use this feature. This source change does not deploy the Worker or publish a client update.

## Shared activity

A board socket accepts `{type:'activity',activity:{kind:'conversation'|'canvas',id,sequence,...}}`. Identity is assigned by the server. Only active editors may publish. Conversation reports additionally require the matching running task initiator and executor login session. The service broadcasts `{type:'activity',activity}` to currently authorized members without updating canvas/document revision. `welcome.activities` restores the latest reports. Reports are monotonically sequenced per epoch/user/kind/id; stale duplicates are ignored. At most 100 reports are retained per room across epochs; clients only receive their current epoch. Socket rate is capped at 20 reports/second. Allowed fields contain public textual progress and bounded task status only, never reasoning or raw tool arguments. Canvas execution remains local; reports do not delegate task control.
