# Hindsight 本地接入验证报告

2026-11-07。结论：**NO_GO，暂不进入产品记忆架构和前端设置改造。** 紧凑配置在这组中文合成语料上达到 95% 的来源召回命中率，检索延迟很好；但语义改写相对现有系统仅提升 7.1 个百分点，未达到预先规定的 10 个百分点，且空闲 RSS 仍超过 1GiB，未达到 768MiB 目标。问题没有通过删题或降低门槛掩盖。

本轮只修改独立功能分支 `codex/feat/hindsight-local-validation-20261107` 的实验脚本与文档，基于本地 main `9035f11cf`。没有改正式记忆库、产品代码、界面、版本和发布配置，没有启动或替换共享客户端。所有输入为人工合成办公资料，没有导入真实聊天。

**实测结果**

| 指标 | 现有 MemoryRetriever | Hindsight 首轮：FP32 + 四路融合 | Hindsight 紧凑配置：INT8 + 语义/关键词 |
|---|---:|---:|---:|
| 有答案问题 top-5 完整来源命中 | 35/40，87.5% | 7/40，17.5% | 38/40，95.0% |
| 语义改写子集 | 12/14，85.7% | 0/14，0% | 13/14，92.9% |
| 同为 1,200 UTF-8 字节上下文预算 | 87.5% | 17.5% | 95.0% |
| 无答案问题仍返回候选 | 5/6 | 6/6 | 6/6 |
| 顺序检索 p50 / p95 | 未作为本轮性能对照 | 19.8 / 23.4ms | 15.7 / 18.5ms |
| 三并发检索 p50 / p95 | — | 24.1 / 40.6ms | 17.3 / 18.9ms |
| 顺序样本数 / 超时数 | — | 138 / 0 | 138 / 0 |

命中率按去重后的**来源文档**计算，多依据题必须全部命中。这是证据检索测试，不是最终回答正确率测试。无答案问题返回候选不等于已经产生幻觉，但说明后续还需要“相关才注入”和拒答机制。未经测试，不能宣称聊天质量提升 95%。

紧凑配置的两道未完整命中题：

- “任务做到一半，需要每隔几分钟打断我报进度吗？”未找回“只在失败、完成或需处理时提醒”的偏好，说明否定式、间接表达仍有漏召回。
- “晨星周报用哪段数据，写给领导时又应先讲什么？”找到了统计周期，没有在 top-5 中同时找到“先给结论”的偏好。它按失败计数，没有把找到半份依据算作通过。

首轮差的主要可见原因是融合排序，而不是中文向量完全失效：多道题的正确来源在语义通道排第 1，却在 graph/temporal 融合后被压低。仅作事后诊断、按原始语义分数重排可命中 38/40；这个诊断分数没有用于晋级。首轮使用的是为降低本地成本选择的 RRF 配置，**不是 Hindsight 默认神经重排器的全面评测**。

只做了一轮针对性配置改进：使用同一 multilingual-e5-small 的官方 INT8 ONNX 文件，并关闭 graph/temporal 检索臂。重新建立独立 bank 并导入全部语料，避免两种精度的索引混用。两项配置同时变化，而且远程抽取重跑存在随机性，不能把改善精确归因于单一参数；这也不是一次证明图检索普遍无效的实验。

**资源和运行成本**

机器为 Apple M2 Max、12 核 CPU、96GiB 内存；Python 3.12.13、Hindsight API slim 1.2.0、PostgreSQL 18.1.0 / pgvector、CPU ONNX；没有使用 GPU。

| 紧凑配置资源项 | 实测 | 预设门槛 / 解释 |
|---|---:|---|
| 空闲进程树 RSS | 常见约 1.08–1.18GiB；最高约 1,206MiB | ≤768MiB，未通过 |
| 本批任务峰值 RSS | 约 1,254MiB，约 1.22GiB | ≤1.5GiB，通过 |
| 缓存重启就绪 | 8.42 秒；额外资源复核启动 13.69 秒 | ≤15 秒，本次样本通过；不是启动 p95 |
| 空闲 CPU | 约单核的 0.65% | 20 秒独立复核，排除监督脚本 CPU |
| 持续检索 CPU | 约 2.24 个逻辑核心 | 10 秒单问题连续请求，共 895 次；是压力诊断，不代表日常平均 |
| 实验环境磁盘 | 约 1.71GiB | 含 Python 环境、两套权重、数据库与 pg0 原生二进制；不是最终安装包大小 |

RSS 是服务、数据库及监督进程的求和，共享页可能重复计算；本机权限不允许取得这些进程的 USS，因此不能把它等同于精确的独占物理内存。原始 CPU 汇总曾包含监督脚本高频枚举进程的成本，已废弃该 CPU 读数；修正后单独记录监督与引擎 CPU，并追加独立复核，召回成绩和资源门槛没有调整。先前的 RSS 和检索耗时仍保留。

磁盘明细约为：独立 Python 环境 1.025GiB，模型缓存 593MiB，数据库 70MiB，`~/.pg0/installation/18.1.0` 原生运行时 41.5MiB。模型缓存同时保留 470,268,510 字节的 FP32 权重和 118,346,824 字节的 INT8 权重；最终打包可选择单一配置，但本轮没有验证打包或分发体积。uv 的共享安装下载缓存不计入上述专用环境体积。

首次安装下载明显慢于日常使用：依赖准备约 6 分 9 秒、安装 189 个包；HF Xet 通道曾停滞，切换普通 HTTP 后完成模型下载，期间触发默认 300 秒模型初始化超时。预缓存后正常启动。桌面集成若继续，应该采用可恢复的模型下载、明确的安装进度、校验及本地路径，避免让用户面对无反馈启动。失败日志已保留。

46 条写入首轮全部成功，耗时 52.69 秒；紧凑配置全部成功，耗时 85.17 秒。单条写入中位约 2.25 秒、p95 约 3.76 秒，最长一次 40.65 秒。远程抽取存在长尾，不能阻塞聊天提交。两轮 API 分别报告约 16.08 万和 16.15 万 total tokens，其中每轮 input tokens 为 158,794；这些是服务报告值，不是账单核对结果。已有结构化记忆若直接迁移，应另测不重复抽取的路径，不能把本轮费用直接外推为最终产品费用。

**控制能力的实际边界**

- 账户使用独立 bank，项目/global 使用严格标签筛选；原始召回候选未发现账户或项目串用。此处验证的是调用方正确指定范围后的检索隔离，单用户本机服务未配置多租户鉴权，bank ID 本身不是访问授权。
- 紧凑配置在两道当前状态题的原始 top-5 中带回了已替代记录；经过宿主原始记录的状态过滤后为 0。这项正确性来自 EWork 治理层，不能算成引擎自动解决冲突。
- 写入→召回→删除→不再召回→明确重建→再次召回→再删除，实测通过。服务重启后已删除记录未重新出现，其他已保存记录仍能找回。
- 停止服务后，实验适配脚本约 29ms 检测到连接失败，约 33ms 内用原有召回器给出降级结果。这只是实验脚本验证，正式客户端尚未接入该降级机制。
- 自动 observation 归纳关闭；没有证明后台反思、长期知识整合、记忆污染抵抗或上万条规模下的表现。

**建议的下一步**

当前应继续保留现有记忆存储与治理层，包括账户和项目边界、手动编辑锁定、来源、版本、替代状态、删除抑制及最终注入预算。Hindsight 暂时保留为实验引擎，不作为桌面端默认常驻组件。

优先解决这次已确认的问题：通用偏好挤占相关项目记忆、否定式改写漏召回、多依据组合和无答案时的过度召回。下一轮更值得验证的是在现有存储上增加轻量多语言向量检索、相关性门槛和多依据检索，然后与 Hindsight 放到同一个冻结基准中比较。Hindsight 可作为有独立服务资源的团队增强方案继续评估；本次没有验证该服务端部署，也没有立即切换到其他开源框架。

按用户“验证通过后再改造”的条件，本轮不启动正式架构迁移和前端设置改造。后续前端仍应围绕读/写开关、个人/项目范围、来源和版本、临时聊天、删除与停用来设计，不能用界面包装弥补尚未通过的引擎指标。
